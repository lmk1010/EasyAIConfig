# DeepSeek Agent 产品经理岗位 — 职责理解与思路

## a. Agent 场景定义与策略闭环

### 高价值场景判断

当前 Agent 产品正从"demo 级"走向"可靠级"，我认为最具商业价值的场景按优先级排列：

1. **编程 Agent（Code Agent）**— 最成熟、用户付费意愿最强，Claude Code / Cursor / Codex 已验证 PMF
2. **Deep Research** — 信息密集型决策场景（投研、学术、竞品分析），用户对"深度+准确"有刚需
3. **个人助理 / 生活 Agent** — 长期高频但可靠性门槛极高，需要跨 session 记忆 + 多工具编排
4. **自动化工作流** — 企业场景，RPA 升级版，核心是确定性和可审计性
5. **多模态设备控制** — Computer Use 方向，潜力大但当前模型能力仍有明显 gap

### 策略闭环方法论

```
场景洞察 → 能力 Gap 分析 → 评测体系设计 → 训练数据方案 → 模型迭代 → 线上验证 → 回到场景
```

**评测体系设计思路：**

| 维度 | 指标示例 | 数据来源 |
|------|---------|---------|
| 任务完成率 | end-to-end success rate | 真实用户 session 回放 |
| 工具调用准确性 | tool call precision/recall | 标注 + 自动化判定 |
| 规划合理性 | plan quality score (人工 + LLM-as-judge) | 对比 baseline |
| 鲁棒性 | 错误恢复率、重试收敛速度 | 故障注入测试 |
| 用户体验 | 交互轮次、等待时间、满意度 | 埋点 + 用户反馈 |

**训练数据方案核心思路：**

- 从真实用户 session 中挖掘高质量 trajectory（成功路径 + 失败路径对比）
- 构造 hard negative：看似合理但会导致失败的 plan/tool call
- 针对性补数据：长链路任务、错误恢复、多工具协调等薄弱环节
- 合成数据 + 人工标注结合，用 reward model 做质量过滤

## b. 技术判断力与竞品洞察

### Agent 核心机制理解

| 机制 | 关键挑战 | 当前前沿做法 |
|------|---------|-------------|
| **Tool Use** | 参数生成准确性、工具选择、错误处理 | 结构化 schema + few-shot + 自动重试 |
| **Planning** | 长链路规划退化、过度规划 vs 欠规划 | ReAct / Plan-then-Execute 混合、动态 re-plan |
| **长期记忆** | 跨 session 连续性、记忆检索准确性 | MEMORY.md 模式、向量检索 + 摘要压缩 |
| **Multi-Agent** | 通信开销、任务分配、结果聚合 | 主从架构（orchestrator + workers）、并行派遣 |

### 竞品深度分析

**Claude Code（Anthropic）：**
- 优势：工具调用极其可靠，错误恢复能力强，上下文管理（compact）优秀
- 策略：重度依赖 system prompt 工程 + 严格的 safety guardrails
- 可借鉴：验证闭环（edit → typecheck → test）、service_scan 防重复启动

**Manus：**
- 优势：端到端自动化体验好，"给个需求就出结果"
- 劣势：中间过程不可控，失败时用户无法介入
- 启示：需要在"自动化程度"和"用户可控性"之间找平衡

**OpenClaw / 个人助理类：**
- 核心难点：跨 session 记忆一致性、个性化偏好建模、多设备/多 App 协调
- 当前瓶颈：模型对"何时该记住 vs 遗忘"缺乏判断力

### 能力瓶颈体系化认知

当前 Agent 模型的 Top 3 瓶颈：

1. **长链路可靠性衰减** — 超过 10 步的任务，成功率显著下降
2. **错误归因与恢复** — 模型倾向于重试相同策略，而非分析根因换思路
3. **上下文窗口管理** — 长对话中关键信息被"淹没"，导致重复错误

## c. 问题拆解与跨团队推进

### 示例：跨 Session 记忆连续性

**模糊痛点：** "Agent 记不住之前聊过的事"

**拆解为具体 Gap：**

```
痛点
├── 模型能力 Gap
│   ├── 缺乏"什么值得记住"的判断力（记忆写入决策）
│   ├── 长文本中关键信息提取不准（记忆压缩）
│   └── 检索到记忆后无法正确融入当前上下文（记忆使用）
│
├── 数据构造方案
│   ├── 构造"跨 session 对话对"训练数据
│   ├── 标注"应该记住 vs 不该记住"的正负样本
│   └── 合成"记忆检索 + 应用"的 trajectory
│
└── 评测指标
    ├── 记忆写入 F1（该记的记了，不该记的没记）
    ├── 记忆检索 recall@k
    └── 端到端：跨 session 任务连续性成功率
```

### 示例：多工具调度可靠性

**模糊痛点：** "Agent 调工具经常出错"

**拆解：**

| 子问题 | 模型 Gap | 数据方案 | 评测指标 |
|--------|---------|---------|---------|
| 工具选择错误 | 对工具能力边界理解不清 | 构造"相似工具对比选择"数据 | tool selection accuracy |
| 参数填充错误 | schema 理解 + 上下文提取不准 | 标注正确/错误参数对 | param exact match rate |
| 错误处理不当 | 遇到 error 后策略单一 | 构造"失败→分析→换策略"trajectory | error recovery success rate |
| 并行调度混乱 | 依赖关系判断错误 | 构造有/无依赖的工具调用序列 | dependency violation rate |

### 跨团队协作方式

```
产品经理（我）          研发团队              数据团队
    │                    │                    │
    ├─ 场景定义 + Gap 分析 ─→                    │
    │                    │                    │
    ├─ 评测指标设计 ────────→ 评测框架实现        │
    │                    │                    │
    ├─ 数据需求文档 ─────────────────────────────→ 数据构造
    │                    │                    │
    │                    ←─ 模型训练 ←──────────── 数据交付
    │                    │                    │
    ←── 评测结果 ─────────┤                    │
    │                    │                    │
    ├─ 分析 + 迭代方向 ──→ 下一轮训练            │
    │                    │                    │
    └─ 线上 A/B + 用户反馈 → 闭环               │
```

**关键原则：**
- 用数据说话，不用直觉争论
- 每个迭代周期控制在 1-2 周，快速验证
- 评测先行：先有评测体系，再做优化，否则无法衡量进步
